# 生图与改图需求

已确认功能需求；对应[技术设计](../technical/image-generation.md)。实际部署、启用与验收以[STATUS](../STATUS.md)为准。

## 1 用户体验

| 场景 | 需求 |
| --- | --- |
| 生图 | 说“画一张……”后生成图片，保存作品并发回当前会话。描述不够明确时按必要程度澄清，不把已有素材冒充新作品。 |
| 改图 | 使用主人提供或明确引用、当前有权取得的图片，按要求修改并保存结果，发回当前会话；指代不清或素材不可取得时先说明。 |
| 查看作品 | 同一伙伴维护一份作品档案，已关联的QQ、ClawChat主人可查询已保存的作品。作品和表情库分别管理，加入表情库仍需明确要求。 |
| 触发与数量 | 首轮仅接受明确请求，默认一次一张；不因普通聊天、心情变化或后台活动自动生成。多图和后台创作留待后续确认。 |
| 失败或未确认 | 区分生成、作品保存和平台发送的结果；不把本地路径当成已发送，也不把未知结果当作失败后自动重新付费生成。 |

手动请求返回发起会话，完成较慢也不改发到[全局主动消息首选平台](proactive-delivery.md)。明确指定其他目标时，沿用已确认的目标权限规则。

## 2 共用和复用

复用原Aurabot图像生成模块的任务、参考图及作品管理逻辑，适配平台实际模型接口，QQ和ClawChat分别处理参考图获取与媒体发送。保持一套生成业务、一份作品档案，不为ClawChat再维护独立生成器；涉及原QQ假设的代码先核对后做必要适配，不能直接假定原模块可原样接入平台。

主人请求生成并保存的作品属于获准共享成果；另一端未保存、未明确授权的私聊图片不因此自动成为参考图。保留既有作品及来源，切换聊天平台不重新生成。收为表情的规则见[表情包需求](stickers.md)。

## 3 接入前提与用量

接入前先核实平台实际生图、参考图编辑能力，以及本实例认证、费用、可用额度和格式限制，再确定技术方案与真实验收调用。未取得的条件如实列出，与用户确认后推进依赖这些条件的工作。

首轮沿用现有云端模型接入和媒体发送路径，不在实例上加载本地图像模型，不因启用本项变更主对话模型。前台明确生图、改图按实际平台图像用量处理，不占既定5次后台请求额度；具体费用不凭对话次数推算。

生成成功后及时持久保存作品，发送失败时复用已有结果；请求超时、断线等结果不明时保留原记录，不自动另起生成请求。不能承诺上游未提供的局部编辑、精确文字、透明背景或无损保持能力。

## 4 验收重点

1. 在平台条件和用量确认后，分别完成一次真实生图、一次主人提供参考图的修改，默认各一张；保存结果和实际生成内容可检查。
2. 两端主人查询同一份作品，参考图来源和会话权限正确；普通聊天不触发生成，后台自动画图保持关闭。
3. QQ、ClawChat分别核对实际图片投递和可见性；模型生成成功、平台发送确认及客户端呈现分别记录，不能互相替代。
4. 已生成作品可恢复查看和发送，重启保留；超时或未知回执不自动重新生成，切换平台不导致第二次调用。

真实QQ验收仍需另行取得账号接入授权，本次需求确认不包含绑定或登录QQ。
