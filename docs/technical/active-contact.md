# 主动联系开发设计

依据[已确认需求](../requirements/active-contact.md)描述实现与数据归属；实际部署、启用与验收以[STATUS](../STATUS.md)为准。

全局接收位置遵守[统一主动消息设计](../requirements/proactive-delivery.md)。主动搭话继承同一偏好，不保存独立平台设置；其他功能在各自适配时接入同一规则。

共用目标选择、旧scope迁移、两端后台身份和回执接线统一见[共同技术设计](proactive-delivery.md)。本项保留原speakup的触发业务；[B站](bili.md)与[日记](diary.md)各自接同一门禁，不复刻普通主动策略。

## 1 实现选择

使用一个原speakup实例负责普通主动联系，保留原tick/fire、由头选择及沉默规则。在普通主动联系中，现有companion-policy只提供共享限制、预算和任务记录，退出同类独立选题与触发；平台Adapter负责执行和投递。其他业务的现状与后续收敛范围分别保留。

执行顺序：原定时检查 → 本地条件检查 → 原fire产生提示 → 固定目标的DSH Session → 逐次后台调用额度检查 → 发送前复查 → 原通道发送与回执。

不增加调度服务、消息总线、独立数据库或管理页面。沿用现有原生执行、任务、outbox、安装和回退入口；原实现不可用时明确关闭该能力，不回退到第二套自写主动策略。

“保留一个触发入口”针对普通主动联系，不要求将记忆整理、浏览、日记等不同功能硬并成一个新调度框架。

## 3 一份状态及计数

继续使用companion-policy.json，不建立第二个陪伴状态库。

| 数据 | 唯一权威位置与规则 |
| --- | --- |
| 主动搭话开关 | 现有settings增加contactEnabled，仅控制本功能。 |
| 全局主动消息平台 | 同一settings只增加proactivePlatform，初始clawchat。各自动通知读取同一值，不为每个功能再保存平台选择。原getConfig.speakUp读取配置投影，不另存同一组设置。 |
| 时段和频率 | 沿用现有时区、空闲、冷却、共同每日上限。 |
| 首次QQ引导 | 同一状态文件保留一次已引导标记；由账号关联成功提示或首次已关联主人私聊接入。使用稳定的提示身份和现有回执，断线重连不另起提示；本项不新建账号绑定系统。 |
| 最近主人互动 | 现有共享计时，接两端可信主人私聊事件；历史回放、自测、系统任务和其他参与者不刷新。只共享必要时间信息。 |
| 随机计划时间 | 在同一文件增加contact.nextAt等必要计划字段，复用原计划算法。它只能延后候选，不能绕过共同冷却。 |
| 每日主动次数与冷却 | 继续使用days.automaticMessages及lastAutomaticAt，各类主动投递共用。发送预占时只记一次；原count读取此结果，删除原tick的另一次次数递增。 |
| 后台模型请求 | 继续使用现有days.modelRequests和reservations，每次真实请求、续步及重试分别计入，包括记忆整理。 |
| 任务及发送结果 | 复用jobs和现有outbox；固定jobId、目标route、原生输入身份及实际回执。不另建任务状态机。 |

共享状态归属改为实例及其主人，投递平台不参与状态分区；兼容当前含ClawChat route的scope，不因切换目标新建一份计数。原speakup.json保留为迁移/回退资料，不再与共享文件并行维护主人联系次数。迁移时校验已有日次数，已发生的联系不重复累加。

contactEnabled是主动联系自身开关，不自动开启B站、日记或修改memory.automatic；全局paused继续约束全部后台调用。联系模块读取的enabled不等于QQ网关总开关，选择ClawChat时不能因此启动OneBot。

## 4 两端执行和投递

- **目标**：根据全局首选解析已关联主人的可信私聊，初始ClawChat；QQ须已连接、核号且关联同一主人。平台由主人设置，自动生成回合不得自行另选平台或收件人。每个job固定route，切换设置只影响后续任务；旧待发自动投递取消，已确认及不确定回执保留，不改目标续发。
- **输入**：原fire提示交给目标会话；只注入该会话上下文、获准记忆、心情和有权限的真实经历。另一平台原文不作为主动联系素材。
- **执行**：ClawChat复用原生schedule来源及现有任务入口；QQ复用原Hub，同时附带由宿主创建的后台任务身份。共同额度须识别QQ后台回合及续步，不能只识别ClawChat schedule，也不能凭提示词文字判断来源。两端沿用既有后台工具限制，不把主动任务当作主人的手动账号操作。
- **在途任务**：复用现有jobs检查；同一主人尚有未完成的主动任务时只恢复该任务，不再接受新的联系候选。保留同一任务的固定目标，不引入额外锁服务。
- **发送**：ClawChat使用现有outbox投递；QQ保留原Hub发送，现有协调器不再发送第二份QQ正文。QQ原发送返回的message_id需反馈到同一任务；模型结束、activity(out)或试运行结果均不能代替平台确认。原QQ若拆段，保留各段回执，整次联系只占一次名额，部分成功不整条重发。
- **复查与恢复**：生成前、发送前均检查开关、全局暂停、共同计时、次数及目标可用性；额度在每次模型调用前检查。已有有效生成结果可等同一目标恢复后复查投递，不自动再生成。发送结果未知时沿用现有held/uncertain处理，不换ID重发。

固定上游源码使用本地Date和speakup.json；兼容生成产物注入上述时钟、共同状态、执行与回执接缝，不能绕过适配直接启用原文件；保留原QQ聊天、媒体和专属工具实现。首轮验收普通文字主动联系，其他媒体继续遵守已确认的后台限制。

消息在任务记录中标明目标来自首选、发起会话或明确指定，复用同一目标选择函数。切换首选仅撤销尚未开始发送、依赖旧首选的自动投递，保留其业务结果；人工任务和明确指定目标不变。发送中、结果未知或已确认的记录保留原route及回执。B站、日记等自动通知复用这一字段与选择方法，各功能不另存一份平台偏好。

## 5 装配、迁移及数据保留

1. 先做同一份设置、计时和原speakup实例的装配；在可控时钟下验证原tick/fire实际执行，普通问候不依赖B站或日记。
2. 同步替换旧普通share触发和提示，接两端任务身份、预算及唯一投递者。使用同一版本完成切换，不长期保留“原版/自写版”两种运行模式。
3. 迁移旧scope、计划、用量及未完成share记录。已接受任务先按旧身份核对完成或保留不确定状态，再允许原策略创建新任务；不能把同一旧任务作为新候选重跑。
4. 按原update-m2入口更新，新实例默认开启自动联系，已有实例保留已保存偏好；冻结并保留当前日记、经历、任务、用量和回执。回退保留新增数据，恢复后的旧share入口与原tick不能同时运行。

## 6 对应回归

沿用现有测试入口，按[S-A1至S-A8](../requirements/active-contact.md#3-验收条件)验证：一个原实例/触发入口、原函数实际调用、普通问候与沉默、双端计时、北京时间边界、共享次数和逐次模型预算、隐私、唯一投递者、未知回执、重启及保留数据的回退。

尤其验证：QQ后台请求不绕过5次共同额度；任一端新互动能阻止另一端待发主动消息；旧share分支不再创建任务；关闭主动联系仍可按原规则整理记忆。受控测试不改变生产自动开关。

新增交互检查：首次QQ引导一次且未回答不切换；平台选择不改变自动开关；全局首选QQ时ClawChat手动请求仍回原会话；明确指定的提醒及动态发布不改道。查询状态时才解释等待或阻断原因，不为每次本地检查另发通知。

ClawChat由Agent自行触发真实模型检查并核对原平台回执；QQ先用真实SDK和可控网关验证，真实账号范围获准后再联调。回归同时覆盖当前人格、记忆、心情及必要媒体路径；不重复运行与本次无关的全部扩展测试。
