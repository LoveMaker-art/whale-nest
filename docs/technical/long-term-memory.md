# 长期记忆开发技术设计

依据[已确认需求](../requirements/long-term-memory.md)描述实现与数据归属；实际部署、启用与验收以[STATUS](../STATUS.md)为准。

## 1 首轮目标

保留原存储、召回和注入；让当前已验证ClawChat主人会话的获准聊天进入Aurabot原自动整理，之后能通过对话查到、纠正和删除。跨平台共享目标保留，真实QQ随通道接入验收。

首轮先处理新增的真实聊天，旧历史全量回填不作为前置条件；已有长期记忆和聊天记录原样保留。

## 2 直接复用及改动

| 位置 | 改动 |
| --- | --- |
| [原memory模块](../../vendor/aurabot/src/modules/memory/index.js)、[提炼和存储](../../vendor/aurabot/src/features/memory.js) | 继续复用tick/consolidate、提炼、检索、进度和原数据库，不另写记忆引擎 |
| [memory-adapter.mjs](../../src/memory-adapter.mjs) | 集中实现兼容聊天读取、原定时回调包装和缺少的对话管理；实际变大再拆文件 |
| [companion.mjs](../../src/companion.mjs) | 使用原宿主唯一memory模块；QQ使用原Hub流水，ClawChat补持久入站读取与管理工具 |
| [connect-bridge.mjs](../../src/connect-bridge.mjs)、[native-replay.mjs](../../src/native-replay.mjs) | 复用原生只读日志接口，在消息持久化后更新兼容流水 |
| [companion-policy.mjs](../../src/companion-policy.mjs) | 在现有额度控制增加原记忆直接模型调用的识别，继续使用同一份计数 |

不预先增加独立任务框架、管理事务日志、来源版本系统或专门退休状态机。

## 3 最小数据链路

**DSH确认接收的真实聊天 → 兼容流水 → 原memory.tick → 原长期记忆 → 原召回工具/提示注入。**

- 原模块的chatLogDays()/chatLogOf(day)是同步Interface，因此以实例内Aurabot chatlog目录保存简单兼容流水。它只是原模块需要的输入资料，不是第二个长期记忆后端。
- 原宿主恢复后QQ原流水与ClawChat兼容行进入同一原整理器；每份资料保留来源，完整DSH Session仍分开。主人ID由可信关联映射，已有实例切换主人ID必须显式迁移；不自动合并数字相同的外部账号。
- 每行提供原模块要求的时间、chatId、who、uid、text，增加稳定的原消息/事件标识。按[现有身份映射](../../src/routing.mjs)判断人物及会话，不能只凭昵称共享。
- 只纳入获准用户内容；排除记忆提示、运行上下文、工具输出、系统任务和运维自测。助手文本如保留则标记bot，不当作用户事实。语音只使用有来源记录的已确认转写。
- 保留简单读取进度；同一来源不重复追加，已处理前缀不重新排序。先保存兼容行再推进进度，重复读取时按来源标识去重；原模块继续维护自己的提炼进度。
- 原模块的忘记标记和流水清理仅作用于兼容文件，DSH原Session只读。保留来源读取进度，不自动重建已清理的旧流水。长消息和分日按原格式限制转换并验证时区一致。

## 4 自动整理与额度

保留原memory的一个tick定时入口，只在其注册回调外加读取、开关及额度检查；不再另起整理定时器。运行时防止同一整理回调重入，原提炼和批次限制继续使用。

原askModel使用plugin来源直接调用llm.stream，原先只识别schedule任务的额度代码不能直接覆盖。已给原记忆维护执行添加AsyncLocalStorage可信调用标识，在已有门禁中逐次预占实际stream请求，包括原内部重试；保持同一policy对象和用量文件。原生用例已验证标识跨SDK生效，未增加通用后台任务框架。

记忆整理与 B 站自动活动分别读取各自的开关。暂停或额度为零时停止发起新调用，原 tick 内所有记忆后台请求都经过同一门禁。新实例启用定时整理时，按[产品默认策略](../PRODUCT.md#日常相处与共同记忆)把北京时间 21:00 换算为 SDK 进程的本地时区。宿主时区变化时重新核对换算。现有实例的实际开关和额度见[当前状态](../STATUS.md#实例设置)。

## 5 对话纠正和删除

保留remember/recall_memory，补主人管理入口，调用原list/update/remove/handleCommand。校验记录存在、正文及可见范围后再执行，以实际落盘结果回复。

整理与记忆管理的写入简单串行，避免整理中的旧结果覆盖刚纠正或删除的内容；无需阻塞普通文字聊天，也不新增版本冲突协议。

复用原忘记命令和明确匹配的forgottenAt标记，保留原processed进度，防止同一旧流水无条件恢复被删内容。单条删除不宣称能删除所有同义历史，也不删除DSH原文。先验证明确来源的纠正/删除；复杂语义遗忘及历史重建保护按后续实际问题补充，不先增加一套管理屏蔽账本。

## 6 必要验收

| 对应需求 | 通过条件 |
| --- | --- |
| M-01、M-02 | 当前真实聊天经原整理生成记忆，之后由原工具及上下文召回；检查真实存储结果 |
| M-03、M-06 | 对话查询/纠正/删除有效，明确匹配来源的遗忘标记生效；重复处理及普通重启不重复积累 |
| M-04 | 非主人不能读取主人记忆，来源不混淆；实际QQ效果后续单独验收 |
| M-05 | 0额度、暂停无请求；原直接调用及重试消耗共同额度，原M3用量不清零 |
| 数据约束 | 原记忆、Session及已有媒体对话保留，原清理不删除DSH历史 |

在test/sdk.test.mjs、test/companion-policy.test.mjs和已有恢复回归中补相关用例，必要时新增一个针对性测试文件。先用替身验证原生链路，再在已确认范围和额度内做一次真实提炼/召回；未实测不标记启用成功。

## 7 后续保留

旧历史批量回填、更多平台/群聊来源、向量检索和复杂故障恢复不作为首轮前置。失败先保留数据、进度和真实错误，按现有备份及更新流程处理；只有具体问题证明原机制不足时才增加恢复代码。
