# 全局主动消息接收平台

已确认功能需求；对应[技术设计](../technical/proactive-delivery.md)。实际部署、启用与验收以[STATUS](../STATUS.md)为准。

## 1 用户只选择一次

同一伙伴保存一份“主动消息首选平台”，初始为ClawChat。主人可在任一已关联私聊中说“以后主动消息都发QQ”，更新后各项未指定目标的自动通知默认继承；不需要分别设置主动搭话、B站、日记和活动分享。

平台偏好只决定接收位置，不开启对应功能、不登录或绑定新账号、不修改时段和额度，也不改变聊天和记忆的共享范围。

## 2 哪些消息跟随设置

| 场景 | 发送位置 |
| --- | --- |
| 普通对话、手动要求的搜索、语音、图片或其他操作结果 | 返回发起请求的会话，沿用该功能已有权限。 |
| 用户明确指定目标的任务或提醒 | 使用明确指定的位置；已有任务不因首选平台改变而迁移。 |
| 自动问候、自动活动分享、B站消息提醒、日记完成通知 | 未明确指定目标时使用共同首选平台；各功能仍须分别具备启用和发送条件。 |
| QQ空间、ClawChat动态等发布 | 按各自确认的发布平台、权限及受众执行；首选平台只可接收有关通知，不决定公开发布。 |

人工发起的长任务也保留发起会话或明确目标，不因为稍后完成就变成跟随首选平台的自动通知。

明确指定的位置优先；没有指定时，手动操作返回发起会话，自动通知读取全局首选。平台发布由各自功能处理，不进入此私聊通知选择。

## 3 对话操作和首次引导

| 场景 | 用户体验 |
| --- | --- |
| 查询 | “你现在会在哪主动找我？”——说明当前首选平台和主动搭话开关。 |
| 改为QQ | “以后主动消息发QQ。”——QQ已关联且可用时保存一份全局选择，确认“以后的主动消息发到QQ”；功能开关不变。 |
| 改回ClawChat | “以后改到ClawChat找我。”——同样更新全局选择，不要求逐项配置。 |
| QQ尚未关联或不可用 | 明确说明暂时不能切换，保留原选择；不假装已经完成设置。 |
| 首次QQ关联完成 | 在关联成功提示或首次主人私聊回复中，提供一次“以后主动消息发QQ还是ClawChat”的选择。普通聊天已经可以直接在QQ进行。 |
| 用户没有回答 | 保留当前首选平台，不反复询问。后续仍可通过对话修改。 |

首次引导只面向已验证并关联的主人；关联对话已经给出选择时直接确认。断线重连不重复引导，未回答也不自动改成QQ。系统保留一次已引导记录，避免每个模块各问一次。

提示示例：“QQ这边也能聊啦。以后主动消息要发到QQ，还是ClawChat？”回答“QQ”只改变接收位置；若主动搭话仍关闭，确认时一并告知。

## 4 切换和异常表现

- 首选平台用于后续任务。按首选平台生成的自动消息在创建时固定目标，旧待发且尚未开始发送的自动通知撤销旧投递，保留业务结果，不重新生成或自动转发；已有明确目标的人工任务保持原约定。
- 发送中或结果未知的任务保留原目标和回执，先核对原发送状态，不换平台或新编号再发；已送达消息不因切换重复通知。
- 已选择的平台后来暂时断开时保留偏好，不自动改发另一端。未开始的任务等待可用；已经生成的有效结果沿用现有恢复规则。
- 首选平台切换不重置每日次数、模型用量或冷却，也不把两端的完整私聊放进同一个会话。

各功能的“是否自动做”“取什么素材”“多久做一次”仍按各自需求确认；本设计统一的是接收位置，其他功能本身没有因此完成开发。

## 5 验收

1. 一次更改只写一份偏好；主动搭话和已接入该规则的其他自动通知读取同一值。
2. 首选QQ时，在ClawChat发起的普通聊天和手动任务仍回复原会话；明确指定的提醒及平台发布不被改道。
3. 首次QQ关联只引导一次，重连和未回答不造成重复询问或自动切换；选择平台不改变自动开关。
4. 错误目标、临时断线、待发取消及未知回执不会产生双发、跨端转发或重新生成；旧结果和用量保留。
