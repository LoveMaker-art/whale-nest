# 语音消息需求

已确认功能需求；对应[技术设计](../technical/voice.md)。实际部署、启用与验收以[STATUS](../STATUS.md)为准。

## 1 用户体验

| 场景 | 需求 |
| --- | --- |
| 主人发语音 | 取得实际转写后继续理解与对话，内容进入发起平台的当前会话；不能把未识别音频当成已听懂。 |
| 主人要求语音回复 | “用语音告诉我”触发实际合成并发回当前会话；不因全局主动消息首选在另一端而改发。 |
| 普通聊天 | 沿用已确认的自动语音开关和原心情倍率；基础概率15%，自动语音最多80字，明确文字要求优先，已手动发送不再自动重复补发。 |
| 设置默认文字 | 可通过对话关闭自动转语音；此后普通聊天用文字，新的明确语音请求按该次要求处理。 |
| 查看或修改音色 | 使用一份当前音色，两端查询和修改同一设置；平台未提供完整目录时只列已验证音色，新音色先做一次短语合成检查，成功保存才确认。 |
| 失败或未确认 | 如实说明并保留可读文字；沿用原请求和回执处理，不反复合成或另起请求重发。 |

默认音色沿用当前已验证配置，不因本次确认替换现有声音。两端可因平台要求采用不同编码，但不各自维护一套声音身份。

## 2 共用和复用

同一伙伴共用语音识别、合成后端及当前音色，QQ和ClawChat分别适配入站音频、格式与发送回执。现有平台语音接线继续使用；原voice和QQ Hub的语音入口保留，通过后端和通道适配接入，不复制两套语音业务。同一已生成结果按已有请求身份和缓存复用，格式转换不作为再次模型生成。

原已有可选语音后端能力保留；首轮使用已核实的当前平台服务，不并行开启多个默认后端。支持音色列表、权限、格式、费用及限额按实际平台条件核验，不把模型名称或合成成功当作QQ已发送并可播放。

## 3 与其他功能的边界

- 普通对话及明确语音请求回复当前会话；自动通知的接收位置继承[全局首选](proactive-delivery.md)，是否允许用语音仍按各自已确认规则。
- 当前前台自动短语音继续使用原心情效果；不因统一音色就开启后台语音、情绪音色切换或新的生成服务。
- 语音转写不自动广播到另一平台，记忆保存按原权限和规则处理，不作为[首轮日记](diary.md)自动取材来源。
- 语音消息与实时通话分别设计，本项不包含连续音频流、通话接听、打断和重连。

前台语音按实际平台模型用量计费，不占既定5次后台请求额度；后台语音若将来纳入，先确认对应开关、额度和平台能力。

## 4 验收重点

1. 两端读取同一音色设置，修改后两端后续合成使用同一个实际音色；重复合成、重启和发送恢复不重复扣调用或发音频。
2. 入站语音实际转写，明确语音请求实际合成；文字偏好、原心情倍率、自动长度限制及防重复规则有效。
3. 请求和回复留在正确会话，转写失败不伪造内容；合成、平台确认及客户端播放分别验证。
4. 现有ClawChat识别和播放结果保留；QQ按实际网关验证格式与权限，模拟结果不能替代真实QQ播放验收。

现有心情联动规则见[心情需求](mood.md)，已部署来源与待收敛部分见[实现清单](../IMPLEMENTATION-INVENTORY.md)。
